# Design

## Context

URL носителя сейчас собирается в трёх местах одинаково: `latestIndex`-подобный шаблон `baseURL + "/" + kind + "/" + number` в `buildPageData` (сайт и плеер), в `BuildFeed` (enclosure и guid) и в `handleAPI` (`media[].url`). Роуты — `GET /audio/{number}` и `GET /video/{number}`, обработчик `handleMedia` ищет эпизод по номеру и отдаёт файл через `http.ServeContent` (Range, Content-Type по MIME из индекса). В индексе уже есть всё нужное для имени файла: `title` эпизода и расширение `file_path`; на диске имена менять не нужно. Мотивация — `proposal.md`, требования — дельта `specs/podcast-serving`.

Ограничения: Go 1.26 ServeMux с паттернами, distroless без внешних утилит, отсутствие миграций данных, стабильность guid у подкаст-подписчиков.

## Goals / Non-Goals

**Goals:**

- Имя файла с расширением в публичном URL носителя, одинаковое для стриминга и скачивания.
- Имя при сохранении = последний сегмент URL (без `Content-Disposition: attachment`).
- Стабильные guid (`/audio/{n}`, `/video/{n}`) и работа ранее опубликованных ссылок.
- Одна функция построения URL, чтобы сайт, фиды и API не расходились.

**Non-Goals:**

- Переименование файлов на диске и миграция данных.
- Отдельный download-эндпоинт и `Content-Disposition: attachment`.
- 301-редиректы со старого slug на актуальный.
- Поле slug в `episode.yaml` (slug всегда выводится из заголовка).
- Уникализация имени при коллизии транслита (номер уже уникален).

## Decisions

**D1. Имя файла строится из номера, slug заголовка и расширения.**
Новый `slug.go`:

- номер форматируется `%03d` (`39` → `039`, `1000` → `1000`);
- slug — транслит заголовка (таблица RU→Latin: `ж→zh`, `х→kh`, `ц→ts`, `ч→ch`, `ш→sh`, `щ→sch`, `ю→yu`, `я→ya`, `й→y`, `ы→y`, `э→e`, `ё→e`, `ъ/ь` отбрасываются), нижний регистр, всё вне `[a-z0-9]` → `-`, схлопывание повторов, обрезка по последнему дефису до 60 символов;
- расширение — `filepath.Ext(file_path)` в нижнем регистре (то же значение, что даёт MIME-классификацию);
- пустой slug → имя `039.ext` без дефиса.

Функции: `Slugify(title)` и `MediaFilename(number, title, file)`. Альтернатива «хранить имя/slug в базе» отклонена: потребовала бы колонки и миграции, а вычисление детерминировано и уже доступно из индекса. Альтернатива «брать имя файла с диска» отклонена: на диске имена бессмысленные (`zapis.m4a`), и пользователь просил диск не трогать.

**D2. Один канонический URL на стриминг и скачивание, без `attachment`.**
Роуты: `GET /{audio|video}/{number}/{name}` и прежние `GET /{audio|video}/{number}`; оба ведут в один `handleMedia`, имя в третьем сегменте игнорируется (поиск по номеру). `Content-Disposition` не ставится: `inline`-поток с корректным именем в URL сохраняется браузером под именем последнего сегмента, а ссылка «скачать» использует атрибут `download`, который и так заставляет сохранить файл с именем из href. `attachment` на общем URL рискован для `<audio src>` и не даёт ничего сверх. Альтернатива «отдельный `/download/...`» отклонена: два URL на один файл, разный кэш и лишняя маршрутизация; пользователь выбрал один URL для обоих сценариев.

**D3. Один хелпер построения ссылок.**
`MediaURL(baseURL, kind, number, title, file)` → именованный URL; `MediaGUID(baseURL, kind, number)` → номерной URL. `buildPageData` (ссылки и `<audio src>`), `BuildFeed` (enclosure — `MediaURL`, guid — `MediaGUID`) и `handleAPI` (`media[].url` — `MediaURL`) используют только их. Альтернатива «собирать строки в каждом месте» отклонена: именно так появился текущий разнобой.

**D4. guid остаётся номерным — подписки не рвутся.**
`guid` в обоих фидах равен `/audio/{n}` / `/video/{n}` (`isPermaLink="true"`), как сейчас. Enclosure переходит на именованный URL. Подкаст-приложение сопоставляет выпуск по guid и один раз забирает файл по новому enclosure-адресу; дублей не возникает. Номерные роуты сохраняются и как цель guid, и как совместимость со старыми ссылками.

**D5. Slug не фиксируется: смена заголовка меняет канонический URL, старые ссылки живут.**
Поскольку имя сегмента не участвует в поиске, ранее опубликованный URL продолжает отдавать файл (200); сайт, фид и API после рескана начинают выдавать новый slug. Альтернатива «заморозить slug при первой публикации» отклонена: нужна миграция и отдельное поле, а выгоды нет — guid и так стабилен. Побочный эффект: один файл доступен по нескольким именам (номерной + старые slug) — принято, дедупликация скачиваний суточная и не раздувает счётчики.

## Risks / Trade-offs

- [Приложения закэшировали enclosure URL] → guid не меняется, приложение один раз скачает по новому адресу; дублей выпусков нет.
- [Старые именованные ссылки после смены заголовка] → имя игнорируется, ответ 200; канонический URL на сайте обновляется после рескана.
- [Один файл по нескольким URL] → суточная дедупликация (эпизод, носитель, IP, UA) не даёт двойного счёта; осознанный компромисс.
- [Транслит длинного/эмодзи-заголовка] → обрезка по слову до 60, пустой slug → имя из номера; покрывается тестами.
- [Откат на старую версию: именованные URL станут 404] → фиды на старте пересоберутся с номерными enclosure (guid прежний), деградация кратковременная.
- [Некоторые клиенты ориентируются на расширение в URL] → теперь расширение реальное (`.mp4`, `.m4a`), это улучшение по сравнению с текущим URL без расширения.

## Migration Plan

1. Деплой новой версии; схемных миграций нет.
2. При старте кэш фидов пуст — enclosure сразу отдаются в новом виде, guid прежние.
3. Диск и `episode.yaml` не меняются; автор ничего не делает.
4. Откат: вернуть прежний ref; номерные роуты работают, именованные исчезают, фиды после рестарта снова номерные.
