# Design

## Context

Сканер (`scanner.go`) распознаёт эпизоды одним регулярным выражением, зашитым на `.mp3`, и жёстко прописывает каждому эпизоду `Mime: "audio/mpeg"`. Поле `mime` уже проходит весь путь: индекс (`episodes.mime`) → API → enclosure фида (`feed.go` читает `v.Mime`) → `Content-Type` отдачи (`handlers.go` ставит `ep.Mime`). То есть транспорт MIME уже универсален, неуниверсальна только точка входа — сканер. Мотивация — см. proposal.md (Why).

## Goals / Non-Goals

**Goals:**

- Принимать `.aac` и `.m4a` наряду с `.mp3` с теми же конвенциями имени (`YYYY-MM-DD-slug`) и sidecar.
- Корректный MIME на всём публичном контуре (фид, отдача аудио, API) для каждого формата.
- Нулевая миграция данных и полная обратная совместимость для существующих MP3-папок.

**Non-Goals:**

- Транскодирование и конвертация форматов на лету.
- Расширение на другие форматы (`.wav`, `.flac`, `.ogg`) — карта расширений сделает это тривиальным позже, но сейчас не входит в объём.
- Определение MIME по содержимому файла (magic bytes) — формат определяется только расширением.
- Изменение guid, слага или правил метрик — они от расширения не зависят.

## Decisions

**D1. Карта «расширение → MIME» + regex с расширением как группой.**
Регулярное выражение имени обобщается до `^(\d{4}-\d{2}-\d{2})-([a-z0-9]+(?:-[a-z0-9]+)*)\.(mp3|aac|m4a)$`, а MIME берётся из карты `map[string]string{".mp3": "audio/mpeg", ".aac": "audio/aac", ".m4a": "audio/x-m4a"}`. Альтернативы: три отдельных регекса (дублирование шаблона имени), перечисление расширений внутри одного regex без карты (MIME всё равно нужен где-то). Карта — единственное место правды о MIME, новый формат = одна строка.

**D2. Для `.m4a` — `audio/x-m4a`, а не `audio/mp4`.**
Требования Apple Podcasts для M4A-enclosure указывают `audio/x-m4a`; `audio/mp4` — каноничный IANA-тип, который тоже встречается в рекомендациях. Выбран Apple-вариант, потому что основной потребитель фида — подкаст-приложения (Apple задаёт де-факто конвенцию). Оба типа агрегаторы понимают; при несовместимости правка — одна константа в карте D1.

**D3. `handlers.go`: в `http.ServeContent` передавать фактическое имя файла вместо `"episode.mp3"`.**
Content-Type уже ставится явно из индекса, поэтому имя сейчас ни на что не влияет, но ложный хардкод вводит в заблуждение. Заменяется на `filepath.Base(ep.FilePath)`. Альтернатива — не трогать: работоспособность не страдает, но правка тривиальна и убирает ловушку для будущих изменений.

**D4. Оценка длительности — единые 128 kbps для всех форматов.**
AAC обычно кодируют на 64–96 kbps, так что оценка без sidecar для AAC может завышать длительность. Пер-форматные битрейты не вводим: надёжного дефолта нет, а точный путь уже задокументирован — `duration` в sidecar (по-прежнему действует для всех форматов). Альтернатива (парсить длительность из контейнера) отклонена: тянет парсер MP4/ADTS в сервис, чья ценность — отсутствие магии над файлами.

**D5. Валидация контента не вводится.**
Сервис и сегодня не проверяет, что `.mp3` — валидный MPEG: файл публикуется как есть. Для `.aac`/`.m4a` тот же принцип: невалидное аудио — ответственность автора выпуска. Сценарии фикстур используют синтетические байты — сканеру и `ServeContent` содержимое безразлично, ffmpeg для тестов не нужен.

## Risks / Trade-offs

- [Редкий клиент не понимает `audio/x-m4a`] → тип соответствует требованиям Apple Podcasts; правка — одна константа в карте D1, поведение закреплено сценарием спеки.
- [Автор кладёт `.m4a` с видеокодеком или битым потоком] → сервис не валидирует контент (D5); проявится только у слушателя, как и сегодня для битого MP3.
- [Завышенная оценка длительности AAC без sidecar] → задокументировать в README рекомендацию заполнять `duration` в sidecar для AAC (уже существующая практика).
- [Дубликат слага между форматами блокирует рескан целиком] → сознательное поведение, уже реализованное для одинаковых расширений (`seenSlugs`): тишина опаснее явной ошибки. Закрепляется сценарием дельты `episode-publishing`.

## Migration Plan

Схема БД не меняется (колонка `mime` существует). Деплой — замена бинаря: старые MP3-папки ведут себя как раньше, новые файлы подхватываются ближайшим ресканом (старт или `POST /admin/rescan`). Откат — предыдущий бинарь; при откате AAC-эпизоды исчезнут из индекса тем же механизмом, что и удалённые файлы (метрики — вместе с эпизодом, CASCADE).
