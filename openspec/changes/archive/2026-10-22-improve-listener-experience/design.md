# Design

## Context

Сервис — один Go-бинарник с `embed`-шаблоном, SQLite-индексом и плоской структурой пакета `main`. Сайт сегодня — одна страница `web/index.html`, собранная из `pageData` в `handlers.go`; плеер — `<audio>` на каждую карточку, состояние нигде не хранится. Медиа-URL и фиды трогать нельзя: они опубликованы и завязаны на номер выпуска. Управление остаётся файловым: никакой админки и никаких записей в папку подкастов из сервиса.

Ограничения, влияющие на решения:

- один процесс, один SQLite-коннект (`MaxOpenConns(1)`), хобби-нагрузка;
- шаблоны и статика живут в бинарнике через `go:embed`, сборки фронтенда нет;
- тесты обработчиков строят сервер через `httptest` и проверяют HTML строками;
- ключ YouTube API — внешний секрет, которого может не быть на стенде.

## Goals / Non-Goals

**Goals:**

- разделить публичную поверхность на лендинг, архив и страницы выпусков без изменения медиа-URL и фидов;
- дать один постоянный плеер с продолжением, главами и доступным управлением;
- получать главы и просмотры YouTube, не блокируя сайт при сбоях внешнего API;
- отдавать поисковикам уникальные метаданные, карту сайта и структурированную разметку;
- сохранить файловую модель управления контентом.

**Non-Goals:**

- SPA, роутинг на клиенте и сборка фронтенда;
- серверный поиск и пагинация архива (49 выпусков фильтруются на клиенте);
- авторизация, персональные подписки, серверное хранение позиции прослушивания;
- главы в RSS (`podcast:chapters`) и транскрипты;
- видео-плеер на сайте;
- изменение формата `guid`, `enclosure` и медиа-URL.

## Decisions

### D1. Три типа страниц вместо одной

```
GET /                     лендинг: промо, 3 последних, start_here, подписка
GET /episodes             архив: компактные строки + клиентский поиск/фильтры
GET /episodes/{number}    выпуск: ноуты, плеер, главы, скачивания, шеринг
GET /sitemap.xml          карта сайта
GET /robots.txt           robots + Sitemap
GET /static/*             общие CSS/JS из embed
```

Канонический URL выпуска — номерной, без slug: номер уже единственный идентификатор, а slug-сегмент добавил бы второй вариант URL без пользы для индексации. Slug остаётся только в медиа-URL. Альтернатива «оставить одну страницу и добавить якоря» отклонена: якорь не даёт ни OG-превью, ни отдельного canonical, ни осмысленного заголовка в выдаче.

Альтернатива «slug в URL страницы» отложена: потребует решения о редиректах при смене заголовка, а выигрыш для SEO невелик при уникальном `<title>` и H1.

### D2. Шаблоны: layout + три страницы

`web/` делится на `layout.html` (head, шапка, подписка, `<audio>`, мини-панель, футер), `home.html`, `episodes.html`, `episode.html`. Каждая страница — отдельный `template.Template`, собранный из `layout.html` и своего файла, поэтому `{{define "content"}}` не конфликтуют. CSS и JS выносятся в `web/style.css` и `web/app.js`, раздаются по `/static/` с `Cache-Control: public, max-age=300`; инлайн-скриптов в разметке не остаётся.

`pageData` получает общие поля страницы: `PageKind`, `Canonical`, `MetaDescription`, `OGType`, `JSONLD template.JS`, `Subscribe []link`, `Latest []episodeItem`. Это позволяет layout-у одному отвечать за SEO-теги и блок подписки, а страницам — только за контент.

Альтернатива «один шаблон с условиями» отклонена: три разных набора данных и OG-типов превращают его в ветвление.

### D3. Контент лендинга — файлы, а не шаблон

`podcast.yaml` расширяется необязательными `tagline`, `links` (`label` + абсолютный `http(s)` URL), `start_here` (номера). Текст лендинга — `about.md` в корне папки подкастов, рендерится существующим markdown-рендерером с той же санитизацией.

`Channel` и отрендеренный `about.md` хранятся в `Server` под `sync.RWMutex`; `handleRescan` перечитывает их после успешной синхронизации. Ошибка перечитывания логируется, но не заменяет последнее валидное состояние — сайт не падает из-за правки файла. Номера `start_here`, которых нет в индексе, отбрасываются при сборке страницы с предупреждением в лог.

Альтернатива «читать `about.md` на каждый запрос» проще, но даёт файловый I/O на каждый хит и расходится с формулировкой «обновляется ресканом».

### D4. Один `<audio>` и JS-объект плеера

В layout — единственный `<audio preload="none">` без `controls`. Кнопки play на лендинге, в архиве и на странице выпуска несут `data-episode`, `data-src`, `data-title`, `data-duration`; клик заполняет общий элемент и запускает воспроизведение. Инлайн-плеер страницы выпуска — это представление того же состояния, а не второй элемент.

Состояние:

```
localStorage: ht:speed           1 | 1.25 | 1.5 | 1.75 | 2
              ht:pos:<number>    секунды, пишутся раз в 5 с и на pause
память:       currentEpisode, lastBeaconEpisode
```

- продолжение: при старте, если `5 < pos < duration - 10`, ставим `currentTime`; иначе с нуля; кнопка «начать сначала» чистит ключ;
- мини-панель: `IntersectionObserver` на инлайн-плеере; когда он вне вьюпорта и идёт воспроизведение — `position: fixed` панель; закрытие вызывает `pause()` и очищает `src`;
- главы: сервер рендерит `<details>` со списком кнопок `data-start` и декоративные метки на полосе; клик вызывает `seek`;
- Media Session: `navigator.mediaSession.metadata` + обработчики `seekbackward/seekforward` по 15 с;
- доступность: прогресс-бар — `<input type="range">` с `aria-label` и `aria-valuetext`, высота 44 px; стрелки дают ±15 с;
- бикон: на событие `play` отправляется `POST /track/play` с номером; повторные старты не дедуплицируются (как и сейчас);
- все обращения к `localStorage` и `navigator.share` — в `try/catch`, без них плеер работает.

Альтернатива «плеер на каждой карточке» отклонена: несколько `<audio>`, рассинхронизация состояния и невозможность мини-панели.

### D5. Главы и просмотры — отдельный синхронизатор

Новый файл `youtube.go` в пакете `main`:

```
episode.yaml.youtube
        |
        v  extractVideoID (youtu.be, watch, shorts, embed, live)
   [number, video_id]
        |
        v  videos.list?part=snippet,statistics&id=... (<=50 id)
        |
        +--> chapters: parseChapters(snippet.description)
        +--> views:    statistics.viewCount
        |
        v
   youtube_meta (SQLite)
```

`parseChapters` принимает только строки, начинающиеся с `[ч:]мм:сс`, с непустым названием и разделителем `-`, `–`, `—`, `:`, `|`; требует минимум 3 главы и первую на `0:00` — это правило самого YouTube, поэтому ложные срабатывания на таймкодах внутри абзаца маловероятны.

Синхронизатор запускается из `main` горутиной: первый цикл сразу, далее тикер каждые 6 часов; после успешного рескана — внеочередной цикл. Выборка — только эпизоды с `fetched_at IS NULL OR fetched_at < now - 6h`. HTTP-клиент с таймаутом 10 с, ключ передаётся query-параметром, но в логи попадают только статус и число элементов, никогда URL.

Без ключа синхронизатор не создаётся: `EpisodeView.YouTubeViews` остаётся 0, глав нет, сайт и API работают. Ошибка API на цикле логируется и не меняет сохранённые значения.

Альтернатива «тянуть YouTube на каждый запрос страницы» отклонена: внешняя задержка в критическом пути, расход квоты и падение сайта при недоступности Google.

### D6. Хранение YouTube-метаданных

Миграция `0005_youtube_meta.sql`:

```sql
CREATE TABLE youtube_meta (
    number     INTEGER PRIMARY KEY REFERENCES episodes(number) ON DELETE CASCADE,
    video_id   TEXT NOT NULL,
    views      INTEGER NOT NULL DEFAULT 0,
    chapters   TEXT NOT NULL DEFAULT '[]',  -- JSON [{start,title}]
    fetched_at TIMESTAMP
);
```

`ON DELETE CASCADE` даёт требуемое удаление вместе с эпизодом; потеря базы лечится ресканом + новым циклом синхронизации. `ListEpisodesWithCounts` делает `LEFT JOIN youtube_meta` и `COALESCE(views, 0)`, главы разбираются в `[]Chapter` в store-слое.

Альтернатива «колонки в `episodes`» отклонена: YouTube-данные — внешний снимок со своим временем жизни, его не должно затирать обновление эпизода из папки.

### D7. Счётчик и его видимость

`Engagement = downloads.total + plays + youtubeViews` считается в `buildPageData`; шаблон выводит его только при `Engagement > 0`. API всегда отдаёт полную разбивку, включая нули и `youtube_views`, чтобы машинные потребители не зависели от правил отображения.

### D8. SEO без внешних зависимостей

- `sitemap.xml` собирается на запрос из индекса: `/`, `/episodes`, `/episodes/{n}`, `<lastmod>` = `published_at`;
- `robots.txt` — константа с абсолютным `Sitemap:`;
- canonical = `baseURL + path`; для выпуска — `/episodes/{n}`;
- meta description — первые ~160 рун описания, очищенного от markdown-разметки рендерером и strip-тегов; у канала берётся `tagline`, иначе `description`;
- JSON-LD собирается `encoding/json` (`<`, `>`, `&` экранируются в `\u003c` и т.п.) и вставляется как `template.JS`; лендинг — `PodcastSeries`, выпуск — `PodcastEpisode` с `partOfSeries`;
- RSS autodiscovery — в layout, поэтому есть на всех страницах.

Альтернатива «отдавать sitemap статикой» невозможна: набор выпусков меняется файлами.

### D9. Порядок и соседи выпуска

Порядок везде — `published_at DESC, number DESC` (как в существующем `ListEpisodes`). «Следующий» на странице выпуска — элемент с индексом `i-1` (новее), «предыдущий» — `i+1` (старее); на краях ссылка не рисуется. Это ровно тот порядок, который видит слушатель в архиве, и он не требует отдельного запроса.

### D10. Поиск и фильтры на клиенте

Сервер рендерит все строки архива с `data-year`, `data-guests`, `data-video`, `data-search` (номер + заголовок + описание + гости в нижнем регистре). JS скрывает несовпавшие через `hidden`, показывает заглушку при пустом результате. Фильтры и поиск лежат в контейнере, который скрыт, пока на `<html>` нет класса `js` (класс ставится крошечным inline-скриптом в `<head>`); без JS список остаётся полным и читаемым, что и требует спека.

### D11. Тесты и совместимость

- `handlers_test.go`: табличные тесты на новые маршруты, canonical/OG/JSON-LD, sitemap/robots, скрытие нулевого счётчика, 404 страницы выпуска, порядок соседей;
- `youtube_test.go`: извлечение id, парсер глав (валидный, короткий, без 0:00, разные разделители), отсутствие ключа, ошибка API, окно 6 часов;
- `store_test.go`/`store`-тесты: апсерт `youtube_meta`, каскадное удаление, потеря базы;
- `config_test.go`: `tagline`/`links`/`start_here`, ошибки валидации;
- существующие тесты фидов и медиа не меняются: их контракт не затронут.

## Risks / Trade-offs

- **Квота или невалидный ключ YouTube** → синхронизация не чаще 6 часов, батчи до 50 id, ошибки только в лог; просмотры остаются последними известными.
- **Ложные главы из описания** → строгое правило (≥3, первая 0:00, строка целиком), главы не влияют на публикацию и скрыты по умолчанию.
- **Сложность мини-панели и регрессии плеера** → один `<audio>`, изоляция состояния в одном объекте, `IntersectionObserver` с feature-detect, ручная проверка iOS Safari и Android Chrome.
- **localStorage недоступен** (приватный режим) → все обращения в `try/catch`, плеер работает без продолжения и без запоминания скорости.
- **SEO-текст лендинга окажется тонким** → `about.md` живёт в файлах и наполняется автором; шаблон не выдумывает контент.
- **Кэш `/static/*`** → 5 минут; при выкатке новая версия подхватывается без хардкода версий и без риска залипшего старого JS надолго.
- **Старые ссылки `/#ep-N`** → сознательно ломаются; в README и спеке зафиксирован переход на `/episodes/{n}`. Медиа, фиды и guid не меняются, подкаст-приложения ничего не замечают.
- **Один SQLite-коннект** → синхронизатор делает HTTP вне транзакций и короткие апсерты, поэтому не блокирует отдачу страниц.

## Migration Plan

1. Выкатить бинарник с миграцией `0005` — она аддитивная, старые данные не трогает; без ключа YouTube сервис работает как раньше.
2. Добавить в папку подкастов `about.md` и при желании `tagline`, `links`, `start_here`; без них лендинг использует описание канала, три последних выпуска и копирование RSS.
3. Задать `YOUTUBE_API_KEY` в окружении; после старта первый цикл заполнит просмотры и главы, далее — раз в 6 часов.
4. Вызвать `POST /admin/rescan`, чтобы подхватить новый контент и пересобрать кэш фидов.
5. Проверить `/`, `/episodes`, `/episodes/{n}`, `/sitemap.xml`, `/robots.txt`, `/api/episodes` и старые медиа-URL.
6. Откат: вернуть предыдущий бинарник. Схема совместима в обе стороны (`youtube_meta` просто игнорируется), `goose down` не требуется.

## Open Questions

- Нужен ли `lastmod` в sitemap с точностью до времени, а не до даты, — можно решить после первого обхода поисковиком, на контракт не влияет.
- Стоит ли позже добавить slug-сегмент к `/episodes/{n}` для читаемости URL — отложено, требует стратегии редиректов.
