# Design

## Context

Конвейер описания сегодня плоский: `scanner.go` читает `description:` из `episode.yaml` в `Episode.Description`, `store.go` кладёт строку в `episodes.description`, а `handlers.go` подставляет её в `<p>{{.Description}}</p>` (html/template экранирует), в `<description>` фида (encoding/xml экранирует) и в поле `description` JSON API. Markdown нигде не интерпретируется, поля YouTube нет, а счётчики выводятся двумя отдельными цифрами.

Ограничения, важные для выбора решений: Go 1.26, SQLite `modernc.org/sqlite` + goose-миграции, distroless-образ (нужны чистые Go-зависимости без cgo), никакого фронтенд-билда (один встроенный `web/index.html`), автор — единственный источник контента (файлы в папке). Мотивация — см. `proposal.md`, требования — в дельтах `specs/`.

## Goals / Non-Goals

**Goals:**

- Markdown-описание выпуска из файла, рендер в HTML на сайте и в аудиофиде без изменения схемы событий и без миграции данных.
- YouTube-ссылка выпуска: хранение, валидация, показ на сайте, отдача в API.
- Единый счётчик потребления на сайте при сохранении раздельного сбора и раздельных агрегатов в API.
- Совместимость: существующие 49 выпусков с `description:` в `episode.yaml` продолжают публиковаться без правок папки.

**Non-Goals:**

- Markdown для описания канала/герой-блока (`podcast.yaml`) — остаётся плоским текстом.
- Редактор/предпросмотр markdown, хранение отрендеренного HTML в базе.
- YouTube-ссылка в RSS-фидах (пользователь подтвердил: только сайт и API).
- Видеоплеер и бикон просмотра видео.
- Ужесточение модели доверия: контент пишет автор, а не посетитель; защита ограничивается неисполнением активной разметки.

## Decisions

**D1. Источник описания — `description.md` в папке эпизода, с фолбэком на `description:` в meta.**
Сканер читает необязательный `description.md`, тримит и использует как источник; если файла нет — берёт `description:` из `episode.yaml`. Оба источника интерпретируются одинаково — как markdown. Если заданы оба, файл побеждает, а сканер пишет предупреждение в лог (не ошибка синхронизации): иначе автор, добавив файл и забыв убрать поле, не увидит изменений. Альтернатива «оба заданы — ошибка рескана» отклонена: потребовала бы разовой чистки 49 `episode.yaml` ради нулевой функциональной выгоды. Альтернатива «только файл, поле удалить» отклонена по той же причине — ломает существующий прод без выгоды. `description.md` добавляется в набор известных файлов папки, поэтому правило «неупомянутый файл — ошибка» на него не срабатывает. Описание читается при сканировании, значит его правка требует рескана (как и любое поле meta) — это документируется в README.

**D2. Markdown-исходник — канонические данные, HTML рендерится на запрос.**
`episodes.description` продолжает хранить текст (теперь markdown-исходник). Новый `markdown.go` отдаёт `template.HTML` через один пайплайн, используемый сайтом и фидом. Альтернатива «хранить готовый HTML в базе» отклонена: новая колонка, необходимость пересобирать индекс при апгрейде рендерера, ломка сравнения `episodeEqual`; рендер 49 коротких документов на запрос дешевле. Альтернатива «рендерить в браузере JS-библиотекой» отклонена: лишняя зависимость и не решает фид/API.

**D3. Рендерер — goldmark + санитайзинг ссылок по AST.**
`github.com/yuin/goldmark` — чистый Go (distroless, без cgo), CommonMark, активно поддерживается. Включается `html.WithHardWraps()`, чтобы одиночные переводы строк в шоу-ноутах сохранялись как `<br>` (автор пишет текст построчно). Сырой HTML не проходит: без `html.WithUnsafe()` goldmark отбрасывает raw-HTML (`<!-- raw HTML omitted -->`), поэтому `<script>` и обработчики не долетают до браузера. Дополнительно AST-обход проверяет адреса ссылок и картинок: разрешены `http`, `https` (для ссылок также `mailto` и фрагменты/относительные), остальные схемы (`javascript:`, `data:`, `vbscript:`) отбрасываются — ссылка превращается в текст, картинка удаляется. Альтернатива bluemonday отклонена: генерируемая goldmark разметка узкая (p, strong/em, списки, code/pre, blockquote, a, img, заголовки, таблицы), санитайзер добавил бы зависимость ради минимума пользы; 30 строк обхода AST проще покрыть тестами. Альтернативы-рендереры (blackfriday, gomarkdown) отклонены по поддержке.

**D4. YouTube-ссылка — поле `youtube` в `episode.yaml`, неразрушающая миграция.**
Сканер валидирует `net/url`: абсолютный URL, схема `http`/`https`, непустой host; значение хранится без нормализации (youtu.be и youtube.com равноправны), существование ролика не проверяется. В `episodes` добавляется колонка `youtube TEXT NOT NULL DEFAULT ''` миграцией goose `0003_*.sql` (`ADD COLUMN`), существующие строки получают пустую строку. Поле входит в `Episode` и в `episodeEqual`, поэтому правка meta подхватывается ресканом. Сайт выводит действие «Смотреть на YouTube» в ряду ссылок карточки (`target="_blank" rel="noopener noreferrer"`), когда ссылка задана. API отдаёт строку `youtube` (пустая — ссылки нет). В RSS не попадает: идентичность item держится на enclosure/guid, а YouTube-ссылка — витринная, не подкастовая.

**D5. Единый счётчик — вычисляемое поле представления.**
`episodeItem` получает `Engagement = Downloads.Total + Plays`, шаблон выводит одну подпись «Скачиваний и прослушиваний: N». База, события, дедупликация и SQL-агрегаты не меняются; API сохраняет `downloads{audio,video,total}` и `plays`. Сумма может посчитать одного человека дважды (скачал и послушал) — это осознанно: показатель «потребление», а не уникальная аудитория; фиксируется в README.

**D6. Видео-скачивание не меняется.**
Ссылки «Скачать Видео» уже строятся из `EpisodeView.Files` и покрыты `TestHome` (`href …/video/2`, `…/video/3`); на проде их нет только из-за отсутствия видеоносителей. Правок кода нет, существующие проверки сохраняются как регрессия.

**D7. API отдаёт markdown-исходник, без `description_html`.**
API — машинная поверхность; сайт и фид — презентационные. Отдельное HTML-поле удвоило бы payload длинных описаний (49 выпусков) и создало второе каноническое представление. Альтернатива «добавить `description_html`» отклонена как YAGNI; при необходимости добавляется отдельным изменением.

## Risks / Trade-offs

- [Тихий приоритет файла над полем meta] → предупреждение в лог сканера + явное правило в README и спеке.
- [Опасные схемы ссылок в markdown] → AST-санитайзер и тесты на `javascript:`/`data:`; raw HTML отключён в рендерере.
- [Старые описания содержат markdown-значимые символы (обратные кавычки, звёздочки) и после раскатки отформатируются иначе] → принято: текст уже написан в markdown-подобном стиле, hard-wraps сохраняют построчность; автор может поправить текст.
- [YouTube-ссылка может быть не на ролик или мёртвой] → проверяется только форма URL; ответственность автора, документируется.
- [Единый счётчик смешивает семантики скачивания и прослушивания] → в README описано как «потребление»; API сохраняет точную разбивку.
- [Откат на старую версию покажет markdown-исходник как плоский текст] → деградация визуальная, не поломка; колонка `youtube` старой версией игнорируется.

## Migration Plan

1. Деплой новой версии: goose при старте накатывает `0003` (`ADD COLUMN youtube … DEFAULT ''`); существующие эпизоды получают пустую ссылку.
2. Данные папки не мигрируются: `description:` в `episode.yaml` продолжает работать; автор переходит на `description.md` по мере желания.
3. Автор добавляет `description.md` и/или `youtube:` в meta и вызывает `POST /admin/rescan` — индекс подхватывает описание и ссылку.
4. Откат: вернуть прежний ref приложения; лишняя колонка не мешает, описания рендерятся как плоский текст (markdown-разметка будет видна как есть).
