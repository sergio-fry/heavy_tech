# Design

## Context

Meta-модель после episode-meta-layout: `episode.yaml` обязателен, носители 0..1+0..1, участники выпуска живут только в свободном тексте описания в разнородных формах (реальные примеры с прода: «Гость нового выпуска — X», «Кто в выпуске: ведущий …, гостья …», «Участники: …», соло-выпуски). Сайт и API участников не показывают. Мотивация — см. proposal.md.

## Goals / Non-Goals

**Goals:**

- Опциональные `host`/`guests` в meta, сквозной проход в индекс, API и карточку сайта.
- Аддитивная миграция без потери данных.
- Удобный ручной проход автора по 49 выпускам (прогресс-рецепт в README).

**Non-Goals:**

- Автоматическое извлечение участников из описаний и автоправка текста описаний (решение автора — вручную).
- Подстановка ведущего по умолчанию из `podcast.yaml` (автор уже показан в герой-блоке).
- Изменения фида (`itunes:author` остаётся канальным) и Open Graph-тегов.
- Структурные объекты участников (имя+био) — биографии остаются в описании.

## Decisions

**D1. `host` — строка, `guests` — список строк, поля полностью опциональны.**
Выбор за простыми значениями: карточке нужны только имена, биографии остаются в описании (это не дублирование — дублирование факта участия уходит, когда автор при ручном проходе сократит описание). Пустая строка/пустой список = «не указано», без дефолтов: ведущий не подставляется из `podcast.yaml`, чтобы поведение было явным. Альтернатива (объекты `{name, bio}`) отклонена — усложняет meta, UI и ручной проход ради данных, уже живущих в description.

**D2. Хранение: две колонки в `episodes`.**
`host TEXT NOT NULL DEFAULT ''` и `guests TEXT NOT NULL DEFAULT '[]'` (JSON-массив строк). JSON в колонке выбран вместо таблицы `episode_guests`: порядок гостей — часть данных, выборка всегда целиком вместе с эпизодом, отдельная таблица добавила бы join и сортировку без выгоды. Миграция 0003 — `ALTER TABLE ADD COLUMN` (goose, Up/Down), аддитивная, рескан заполняет значения.

**D3. Валидация мягкая, но типизированная.**
YAML-типы проверяются: `host` — строка, `guests` — список строк; иначе — ошибка синхронизации (как для других полей meta). Значения тримятся; после трима пустые — отбрасываются (пустой `guests`-элемент — ошибка: опечатка автора не должна молча исчезать). Семантика имён не проверяется. Неупомянутые участники не влияют на строгие правила папки: `host`/`guests` — поля meta, а не файлы.

**D4. UI: две строки карточки, каждая — по факту наличия.**
Под заголовком (до описания): «Ведущий: …» и «Гости: …» (join «, »). Строка absent → не рендерится вовсе (без пустых лейблов). Экранирование — общим шаблонным механизмом. Формулировки лейблов («Ведущий», «Гости») фиксируются сценариями дельты.

**D5. Ручная миграция контента — вне кода.**
Автор проходит 49 `episode.yaml` сам: переносит имена из описаний в поля, параллельно сокращает описания. Сервису для этого ничего не нужно; README получает схему полей с примером и grep-рецепт прогресса (`grep -L` по папкам без `host`/`guests`). Скрипт-генератор реестра не делаем — один grep покрывает потребность.

## Risks / Trade-offs

- [Ручной проход затянется, часть выпусков долго останется без участников] → поля опциональны, UI деградирует изящно; прогресс виден через grep-рецепт.
- [Имена в двух местах (поле + непересмотренное описание) временно дублируются] → осознанный компромисс решения «вручную»; исчезает по мере прохода.
- [Опечатка в списке гостей (пустой элемент) уйдёт в ошибку рескана] → сознательно: строгая ошибка уже спасала от тихих опечаток.
- [JSON в колонке — не реляционная целостность] → данные производны от папки и пересобираются ресканом; ограничений выборки нет.

## Migration Plan

Миграция 0003 аддитивная (ALTER TABLE), деплой — обычный bump ref в infra. Контентная миграция — ручной проход автора по `episode.yaml` на CT после деплоя, темп не регламентирован.

## Open Questions

Нет — формат (A: простые строки) и способ миграции (вручную) зафиксированы автором до создания change.
