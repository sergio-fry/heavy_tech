# Proposal

## Why

Участники выпусков (ведущий, гости) — пока просто строки в `episode.yaml`. У каждого участника нет ни описания, ни аватарки, ни своей страницы: имя в списке участников выпуска не на что нажать. Пользователь хочет рассматривать участника как полноценную сущность: с описанием и аватаркой (одна аватарка на участника, без повторов), со страницей, куда можно попасть кликом по имени в списке участников выпуска, и где видны его аватар, имя и все выпуски с его участием.

## What Changes

- Появляется каталог участников: `data/podcast/people/<slug>/person.yaml` с обязательным `name` (ключ связи с выпусками), опциональным `avatar` (файл изображения в той же папке) и описанием (`description` в yaml или `description.md` рядом, по аналогии с эпизодами). Каталог необязателен: нет папки `people` — сайт работает как раньше.
- Индекс хранит участников и связи «выпуск ↔ участник» (`people`, `episode_people`); связи пересчитываются при каждом рескане по точному совпадению имени из `host`/`guests` эпизода с `name` участника. Имена без совпадений остаются простым текстом — ошибки нет.
- Сайт: имена известных участников в списках «Ведущий:»/«Гости:» на карточке и странице выпуска становятся ссылками на страницу участника `/people/<slug>`; страница участника показывает аватар, имя, описание и выпуски с его участием (новыми сверху); аватар раздаётся по стабильному URL `/people/<slug>/avatar.<ext>` и хранится один раз на участника.
- API: `GET /api/episodes` аддитивно получает `participants` (роль, имя, и для известных — slug, URL страницы, аватар); новый `GET /api/people` отдаёт машинный список участников; карта сайта пополняется страницами участников.

## Capabilities

### New Capabilities

(нет — участники продолжают жить в существующих capability)

### Modified Capabilities

- `episode-publishing`: каталог участников `people/<slug>/person.yaml` (валидация как у эпизодов) и связь «выпуск ↔ участник» по имени, пересчитываемая при рескане.
- `podcast-serving`: страницы участников и аватары, интерактивный список участников на сайте, `participants`/`/api/people` в API, страницы участников в карте сайта.

## Impact

- Код: `scanner.go` (сканирование `people/`), миграция `migrations/0006_people.sql`, `store.go` (`Person`, `SyncPeople`, связи), `handlers.go` (роуты `/people/{slug}`, `/people/{slug}/avatar.<ext>`, `/api/people`), `pages.go` (страница участника), `seo.go`/`sitemap` (URL участников), `web/` (карточка/страница выпуска — ссылки на участников, `person.html`), `style.css`.
- БД: аддитивная миграция, данные не теряются; связи пересчитываются целиком в транзакции рескана.
- Контент: автор заводит `people/<slug>/` по желанию; существующие выпуски продолжают работать без изменений.
- Фид не меняется: участники — поверхность сайта и API.
