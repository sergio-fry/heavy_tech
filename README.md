# heavytech

Публикатор подкаста из статичной папки: Go-сервис, который раздаёт готовые
аудио- и видеофайлы (MP3/AAC и MP4/MKV/WebM), отдаёт два RSS-фида для
подкаст-приложений, показывает лендинг, архив и страницы выпусков с единым
плеером и считает скачивания, прослушивания и просмотры на YouTube. Дополняет студию записи
[Tributary](https://github.com/Realmullens/tributary): записал выпуск — положил
файлы в папку — сервис его публикует.

Управление — **через файлы**: никакой админки. Пользовательская история — через
публичный API и сайт.

## Как это работает

```
data/podcast/                 <- источник истины
  podcast.yaml                <- метаданные канала (обязателен)
  about.md                    <- необязательный текст лендинга
  1/                          <- выпуск №1: папка = эпизод = номер
    episode.yaml              <- обязательный манифест выпуска
    zapis.m4a                 <- аудио (0..1)
    efir.mp4                  <- видео (0..1)
  2/
    episode.yaml
    zapis.aac
data/heavytech.db             <- SQLite: производный индекс + метрики
```

- Сканер при старте и по `POST /admin/rescan` синхронизирует индекс с папкой:
  новые папки добавляются, исчезнувшие удаляются (носители и метрики удаляются
  вместе с эпизодом — CASCADE), изменившиеся (size+mtime/поля meta) обновляются.
- SQLite — только индекс и события; удаление базы нестрашно для контента:
  индекс восстановится ресканом (метрики начнутся с нуля).

## Конвенции папки

### Папка эпизода: имя = номер выпуска

- имя папки — `^[1-9][0-9]*$`: `1`, `2`, `42`; `0` и ведущие нули (`007`) —
  ошибка синхронизации;
- нецифровые папки (`chernoviki`) игнорируются — в них можно держать что угодно;
- **номер — единственный идентификатор** выпуска: он попадает в URL и guid;
- **⚠️ номер неизменяем после публикации.** Переименование папки = удаление
  старого эпизода и добавление нового (новый guid, счётчики с нуля).
- плоские медиафайлы в корне папки подкастов не индексируются (остатки прежнего
  layout; см. «Миграция»).

Внутри папки обязателен `episode.yaml`:

```yaml
title: Первый выпуск          # обязателен
published_at: 2026-10-01      # обязателен, YYYY-MM-DD
host: Сергей Удалов           # опционально: ведущий выпуска
guests:                       # опционально: гости, порядок = порядок на сайте
  - Мила Шведова
description: О чём выпуск     # legacy-фолбэк описания; приоритет у description.md
youtube: https://youtu.be/... # опционально: ссылка на видеоверсию выпуска
audio:                        # секция опциональна, но нужна хотя бы одна из audio/video
  file: zapis.m4a             # имя файла в этой же папке; обязательно в секции
  duration: 1872              # секунды; опционально
  bitrate_kbps: 96            # опционально, информационно
video:
  file: efir.mp4
  resolution: 1920x1080       # опционально, информационно
```

Правила валидации: максимум один `audio` и один `video`; `file` обязан
существовать в папке эпизода; расширение обязано соответствовать секции;
`duration`/`bitrate_kbps`/`resolution` сканер не проверяет — это декларация.
`youtube` — необязательный абсолютный `http(s)` URL с хостом (иначе ошибка
синхронизации); существование ролика не проверяется. `host` — строка, `guests` —
список строк без пустых элементов (иначе ошибка синхронизации); участники выводятся
на карточке выпуска («Ведущий: …», «Гости: …») и в `/api/episodes`; без полей линии
не рисуются. Любой не упомянутый в meta файл (кроме dot-файлов и `description.md`) —
ошибка синхронизации; dot-файлы (scp-временки) игнорируются.

#### Участники выпуска: ручной перенос из описаний

Исторически имена гостей зашиты в текст описаний. Поля `host`/`guests` заполняются
вручную: при проходе по выпускам переносите имена в поля и сокращайте описание,
чтобы факт участия не дублировался в двух местах. Прогресс прохода — выпуски без
`host`:

```bash
grep -L '^host:' /mnt/storage/heavytech/data/podcast/*/episode.yaml
```

### Описание выпуска: `description.md`

Описание выпуска (шоу-ноуты) можно держать в markdown-файле `description.md`
рядом с `episode.yaml`. Он необязателен, но если есть — его содержимое побеждает
поле `description:` (при обоих сканер пишет предупреждение в лог). Форматирование
рендерится в HTML на сайте и в аудиофиде: абзацы и переносы строк, списки,
выделение, ссылки; сырой HTML и опасные схемы ссылок не исполняются.

```md
Гость выпуска — **Иван**, автор [проекта](https://example.com).

- 00:00 — вступление
- 12:30 — main часть
```

`description:` в `episode.yaml` остаётся фолбэком для старых выпусков и тоже
интерпретируется как markdown. Описание читается при сканировании: после правки
`description.md` нужен рескан (`POST /admin/rescan`), как и для любого поля meta.

Классификация носителей по расширению:

| расширение | вид | MIME |
|---|---|---|
| `.mp3` | audio | `audio/mpeg` |
| `.aac` | audio | `audio/aac` |
| `.m4a` | audio | `audio/x-m4a` |
| `.mp4` | video | `video/mp4` |
| `.mov` | video | `video/quicktime` |
| `.mkv` | video | `video/x-matroska` |
| `.webm` | video | `video/webm` |

### `podcast.yaml` (обязателен)

<!-- podcast-yaml-example:start -->
```yaml
title: Heavy Tech
description: Подкаст о тяжёлом в технологиях
author: Сергей Удалов
email: sergey@example.com    # для itunes:owner
image: https://.../cover.png # абсолютный URL обложки (от 1400x1400 для Apple)
category: Technology
explicit: false
link: https://show.example.com  # необязательно; иначе base-url
tagline: Разговоры о разработке # необязательно: подзаголовок и meta description
links:                          # необязательно: кнопки подписки
  - label: Apple Podcasts
    url: https://podcasts.apple.com/...
  - label: Telegram
    url: https://t.me/...
start_here: [49, 47, 45]        # необязательно: подборка «с чего начать»
```
<!-- podcast-yaml-example:end -->

`tagline` — короткая строка для `<title>`/meta description лендинга. `links` —
кнопки подписки в заданном порядке: у каждой обязателен непустой `label` и
абсолютный `http(s)` URL, иначе сервис не стартует с ошибкой конфигурации.
`start_here` — номера выпусков для подборки новичку: порядок сохраняется,
номера, которых нет в индексе, пропускаются с предупреждением в лог.

Без файла или с пустыми `title`/`description` сервис не стартует: канал без
метаданных не публикуется.

### Текст лендинга: `about.md`

В корне папки подкастов может лежать `about.md` — markdown-текст лендинга
(промо, «о подкасте», ссылки). Он рендерится тем же безопасным рендерером, что
и описания выпусков: сырой HTML не исполняется. Файл читается при старте и
перечитывается по `POST /admin/rescan`, перезапуск не нужен. Без файла лендинг
показывает `description` канала.

## Запуск

```bash
go build -o heavytech .
./heavytech \
  -addr :8080 \
  -base-url https://show.example.com \   # публичный URL для абсолютных ссылок
  -podcast-dir data/podcast \
  -db data/heavytech.db \
  -youtube-api-key "$YOUTUBE_API_KEY"    # необязательно
```

Те же параметры через ENV: `ADDR`, `BASE_URL`, `PODCAST_DIR`, `DB_PATH`,
`YOUTUBE_API_KEY`.

Без `YOUTUBE_API_KEY` сервис работает полностью: сайт, фиды, API и медиа
доступны, просто нет глав и просмотров YouTube — в лог пишется одна строка
`youtube: ключ не задан — главы и просмотры отключены`.

`-base-url` должен быть настоящим публичным адресом: из него строятся
абсолютные URL в фидах и API — подкаст-приложения ходят в фид снаружи.

## Эндпоинты

| Метод и путь | Что это |
|---|---|
| `GET /` | лендинг: промо-текст из `about.md`, три последних выпуска, подборка `start_here`, подписка |
| `GET /episodes` | архив всех выпусков: поиск и фильтры по году, гостям и видео |
| `GET /episodes/{номер}` | страница выпуска: ноуты, плеер с главами, скачивания, шеринг |
| `GET /sitemap.xml` | карта сайта: лендинг, архив, все выпуски |
| `GET /robots.txt` | разрешение обхода и абсолютная ссылка на карту сайта |
| `GET /static/*` | встроенные CSS/JS (`Cache-Control: max-age=300`) |
| `GET /feed.xml` | RSS 2.0 + iTunes для выпусков **с аудио** |
| `GET /feed-video.xml` | RSS 2.0 + iTunes для выпусков **с видео** |
| `GET /audio/{номер}/{имя}.{ext}` | аудио с поддержкой Range (стриминг и скачивание) |
| `GET /video/{номер}/{имя}.{ext}` | видео с поддержкой Range (стриминг и скачивание) |
| `GET /audio/{номер}`, `GET /video/{номер}` | стабильные номерные URL (guid в фидах, старые ссылки) |
| `POST /track/play` | бикон плеера, JSON `{"episode": 7, "progress": 0..100?}` (= прослушивание) |
| `GET /api/episodes` | JSON-список выпусков: markdown-описание, `youtube`, счётчики, `youtube_views`, `chapters` |
| `POST /admin/rescan` | синхронизировать папку с индексом (и перечитать `podcast.yaml`/`about.md`) |

`/audio/{n}` и `/video/{n}` — одновременно стриминг и скачивание: отдельного
эндпоинта нет, приложения и браузер качают тот же URL. Порядок в фидах, на сайте
и в API — по `published_at` (новые сверху), номер порядок не задаёт.

Старые якоря `/#ep-N` больше не используются: постоянная ссылка на выпуск —
`/episodes/{номер}`. Медиа-URL, фиды и их `guid` не менялись, подкаст-приложения
ничего не замечают.

### Плеер и страницы

На странице один `<audio>` без нативного `controls`; кнопки на карточках и в
архиве переключают его. При скролле появляется закреплённая мини-панель
(название, play/pause, перемотка). Плеер продолжает выпуск с последней позиции
(хранится в `localStorage`, кнопка «Начать сначала» сбрасывает), переключает
скорость 1 / 1.25 / 1.5 / 1.75 / 2x, публикует метаданные в Media Session и
перематывается стрелками клавиатуры на ±15 секунд.

Главы приходят из описания YouTube-ролика, показываются отдельным разделом,
закрытым по умолчанию и не попадают в шоу-ноуты. Счётчик потребления
включает скачивания, прослушивания и просмотры YouTube и не выводится, пока
равен нулю.

### Имя файла в медиа-URL

Канонический URL носителя содержит имя файла: `/{audio|video}/{номер}/{имя}.{ext}`,
например `https://heavytech.udalovs.ru/video/39/039-vse-flomastery-raznye.mp4`.
Имя строится из номера (не меньше трёх цифр: `39` → `039`), транслита заголовка
(нижний регистр, `[a-z0-9-]`, обрезка по границе слова до 60 символов) и
реального расширения файла; пустой транслит даёт имя только из номера (`007.m4a`).
Имя на диске не меняется: `zapis.m4a` остаётся как есть, slug вычисляется при
построении ссылок. Один и тот же именованный URL используется для стриминга,
скачивания (ссылка «скачать» с атрибутом `download`), `enclosure` в фидах и
`media[].url` в API — сохранённый файл называется так же, как последний сегмент URL.

`enclosure` в фидах указывает на именованный URL, а `guid` остаётся номерным
(`/audio/{номер}`, `/video/{номер}`): переименование выпуска не создаёт дубль у
подписчиков. Имя в третьем сегменте декоративное — поиск идёт по номеру, поэтому
старые ссылки со прежним slug продолжают работать.

Всё публично и без авторизации. Если захочется прикрыть статистику — basic auth
вешается на reverse-proxy, код сервиса не меняется.

## Добавление выпуска (эксплуатация)

Управление — через файлы, без админки. Папка подкастов живёт на CT `heavytech`
на data-диске, в `/mnt/storage/heavytech/data/podcast/`; конвенции папок,
`episode.yaml` и `podcast.yaml` — выше.

**Канал.** `title`/`description` из `podcast.yaml` попадают в герой-блок сайта
и OG-теги, `image` (абсолютный URL, от 1400x1400 для Apple) — в обложку героя
и `og:image`. Файл правится руками на CT; роль при деплое его не затирает.

**Выпуск:**

1. Придумать следующий свободный номер и создать папку `<номер>`.
2. Положить в неё носители (аудио и/или видео) и `episode.yaml` с `title`,
   `published_at` и секциями. Реальную длительность можно снять:
   `ffprobe -v error -show_entries format=duration -of csv=p=0 zapis.m4a`.
   Без `duration` для аудио длительность оценивается по размеру из расчёта
   128 kbps — для AAC (обычно 64–96 kbps) оценка завышает, стоит заполнять.
3. Скопировать на CT и выставить владельца nonroot (65532), чтобы сканер мог
   удалять и заменять файлы:

   ```bash
   scp -r 42 podcast.yaml \
       root@192.168.88.134:/mnt/storage/heavytech/data/podcast/
   ssh root@192.168.88.134 chown -R 65532:65532 \
       /mnt/storage/heavytech/data/podcast/42
   ```

4. Синхронизировать индекс и проверить:

   ```bash
   curl -X POST https://heavytech.udalovs.ru/admin/rescan
   # {"added":1,"updated":0,"removed":0,"total":4}
   curl -s https://heavytech.udalovs.ru/ | grep -o 'data-episode="[^"]*"'
   curl -s -o /dev/null -w '%{http_code}\n' https://heavytech.udalovs.ru/episodes/42
   curl -s https://heavytech.udalovs.ru/sitemap.xml | grep -c '/episodes/'
   curl -s https://heavytech.udalovs.ru/feed.xml | grep -c '<item>'
   curl -s https://heavytech.udalovs.ru/feed-video.xml | grep -c '<item>'
   ```

Грабли: отсутствие `episode.yaml`, битый YAML, несуществующий/лишний файл,
`007` вместо `7` — ошибка синхронизации (индекс остаётся прежним); нецифровые
папки и dot-файлы игнорируются; удаление папки после рескана убирает выпуск
вместе с метриками (CASCADE); ID3-теги не читаются — заголовок берётся из meta.

## Миграция на номерной layout (одноразово)

Переход со старого `YYYY-MM-DD-slug.<ext>` (выполняется на сервере до деплоя
номерной версии):

```bash
docker stop heavytech
./scripts/migrate-to-numbers.sh /mnt/storage/heavytech/data/podcast
```

Скрипт уводит `data/heavytech.db` в sidecar-имя с датой (fresh start: старые
guid `/audio/{slug}` умирают, подписчики увидят выпуски как новые), сворачивает
плоские медиафайлы в папки-номера по хронологии (1 = старейший), генерирует
`episode.yaml` (заголовок из слага прежним алгоритмом, `duration` из `ffprobe`
или старого sidecar), переносит старые sidecar-файлы в backup и печатает отчёт.
`podcast.yaml` не трогается. После скрипта — деплой новой версии, рескан
пересоберёт индекс из папок.

Откат: вернуть старый ref приложения; папки уже номерные, содержимое `data/`
восстанавливается из бэкапа.

## YouTube: главы и просмотры

Если у выпуска задан `youtube:`, сервис раз в 6 часов (и сразу при старте, и
после успешного рескана) запрашивает у YouTube Data API описание и статистику
ролика:

- **главы** — строки вида `0:00 Вступление`, `12:30 Основная часть` в описании
  ролика; нужно не меньше трёх глав, первая с `0:00`, время возрастает;
- **просмотры** — `statistics.viewCount`, сохраняются снимком с временем
  получения и входят в единый счётчик на сайте.

Ключ передаётся через `-youtube-api-key` или `YOUTUBE_API_KEY`; в логи и
ответы он не попадает. Запросы батчатся до 50 роликов, таймаут 10 секунд,
квота расходуется по одному вызову `videos.list` на батч. Ошибка или
недоступность API не меняет последние известные значения и не влияет на
отдачу страниц. Без ключа главы и просмотры просто отсутствуют.

## Метрики (честно про точность)

Уровень «личное любопытство», не IAB:

- **Скачивание** — успешный `GET /audio/{n}` или `GET /video/{n}`: один раз в
  сутки (UTC) на комбинацию (эпизод, носитель, IP, User-Agent). Аудио и видео
  считаются раздельно; Range-докачки не раздувают счётчик; HEAD-запросы,
  пустой UA и боты (`bot|spider|crawler|monitor`) не считаются.
- **Прослушивание** — бикон при нажатии play в веб-плеере (только аудио).
- В базе только **сольтированные хеши** IP и UA: сырых персональных данных нет.
- IP берётся из `X-Forwarded-For` (сервис за reverse-proxy), иначе RemoteAddr.
- **Просмотры YouTube** — последний снимок `viewCount` по ролику выпуска,
  обновляется раз в 6 часов; это не событие сервиса, а внешняя статистика.
- **На сайте — единый счётчик «Прослушиваний и просмотров»**: сумма скачиваний
  (аудио + видео), прослушиваний и просмотров YouTube. Пока значение равно нулю,
  счётчик не выводится. Это показатель потребления, а не уникальной аудитории:
  один человек, который и скачал, и послушал, посчитан дважды.
- **В API — раздельные агрегаты**: `downloads{audio,video,total}`, `plays` и
  `youtube_views`. Сбор, дедупликация и хранение событий остаются раздельными
  по видам.

## Деплой

Вне этого репозитория — ansible-роль `heavytech` в infra: bump `heavytech_git_ref`
на новый SHA → `make run ANSIBLE_OPTS="--limit heavytech"` (на CT пересобирается
docker compose из `/opt/heavytech`). Состояние — host-volume `/opt/heavytech/data`
(папка подкастов + SQLite-база), наружу — edge-Caddy `heavytech.udalovs.ru`.
Бэкапить `data/` целиком (папка + база).

Порядок выката этой версии:

1. Собрать и задеплоить бинарник: миграция `0005_youtube_meta.sql` накатится
   автоматически, она аддитивная и старые данные не трогает.
2. При желании добавить в папку подкастов `about.md`, `tagline`, `links`,
   `start_here`; без них лендинг покажет описание канала, три последних
   выпуска и копирование RSS.
3. Задать `YOUTUBE_API_KEY` в окружении контейнера; первый цикл синхронизации
   стартует сразу, дальше — раз в 6 часов.
4. Вызвать `POST /admin/rescan`, чтобы перечитать контент и сбросить кэш фидов.
5. Проверить `/`, `/episodes`, `/episodes/{n}`, `/sitemap.xml`, `/robots.txt`,
   `/api/episodes` и старые медиа-URL.
6. Откат: вернуть предыдущий бинарник. Схема совместима в обе стороны
   (`youtube_meta` просто игнорируется), `goose down` не нужен.
